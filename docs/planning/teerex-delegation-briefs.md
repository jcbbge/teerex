**Prepare small, reusable records and feasibility studies before commissioning new platforms.** H01–H08 below expand the existing historical handoff into delegation-ready scoping tasks; none is a newly assigned project or implementation approval. The paired agent-core migration remains teerex product work with an existing external owner, not a ninth generic project.

Joshua authorized publishing this planning package and preparing outside scopes for later delegation, not selecting manual park/resume or implementing the outside proposals. The filed-issue backlog remains externally owned; no private artifact access is required.

## Shared brief contract

**Authority and provenance.** The original Phase 1–3 suggestions are assistant proposals, not individually commissioned products. Authoritative origins are the physical pages of P1 (12 pages) and P2 (8 pages), identified in the [definitive inventory](https://github.com/jcbbge/teerex/blob/0a09d8759d1e60f3f41f501dad644dd029539d81/docs/planning/teerex-pdf-work-inventory.md). Markdown attachments remain excluded. The [original H01–H08 boundaries](https://github.com/jcbbge/teerex/blob/0a09d8759d1e60f3f41f501dad644dd029539d81/docs/planning/teerex-non-rex-handoff.md) remain historical evidence, not a competing current plan.

**Who can decide.** Joshua selects projects, repositories, recipients, license, private-data access and implementation scope. No outside repository or implementer has been selected here. A delegate receiving one of these briefs can complete its discovery/specification output without starting another agent, creating a repository, deploying software or contacting a personal host. Implementation and publication require the selected scope and destination to be authorized.

**Where the boundary sits.** teerex owns Rex-specific acquisition, explicit target/source identity, supported command semantics, visible resources, lifecycle integration and its acceptance tests. Generic records, policy research, terminal replay and agent-workflow practices can live elsewhere. Prefer an existing repository or plain document over a new library. Do not duplicate externally owned filed issues, agent-core adapters or existing teerex stream/lease code.

**Required delivery.** Each scoping task returns its smallest useful proposed contract, exact source references, a representative sanitized example, acceptance cases including one counterexample, unresolved decisions and a recommendation to reuse, build, defer or reject. Findings must distinguish observed, inferred, supplied and chosen information. A spec is acceptable even when the correct result is “do not build this.”

**Data and rights.** Use synthetic fixtures or explicitly approved sanitized inputs. Raw terminal captures, transcripts, private configuration, credentials, personal host addresses and original private PDFs do not enter public repositories or model-evaluation sets. Official documentation/API indexing is not proprietary Rex application source. No proprietary binary redistribution or libghostty embedding permission is assumed.

The six labels in each brief are Who, What, Why, Where, When and How. Inputs/outputs, acceptance and approval gates then make the scope reviewable.

## H01 — Evidence, investigation and handoff records

**Origins:** Phase 1 #1/#4/#6, A01/A02/A08/A09/A12, P1:pp2,4–5; Phase 2 #2/#8, B05/B15/B16, P1:pp7,10–11. Only the generic portions belong here.

- **Who:** a future evidence/workflow owner; Joshua is the consumer and scope approver. No recipient assigned.
- **What:** specify one manual local record for an investigation, exact experiment evidence, a shipping receipt and a bidirectional handoff. Reuse an existing artifact/file representation where possible.
- **Why:** preserve the next useful experiment and what a check actually established without rereading a conversation.
- **Where:** destination repository undecided. teerex supplies optional bounded observation/run references; this owner does not capture Rex screens, focus panes or own teerex recovery.
- **When:** first external scoping recommendation. It can proceed independently of teerex issues; a teerex park/resume feature does not have to wait for a generic service.
- **How:** model one parked investigation and one failed/successful experiment pair manually, then identify the minimum shared fields rather than designing a database first.

**Inputs and outputs.** Inputs: synthetic question, hypothesis, next experiment, repository/commit or artifact identity, named check/result, omitted checks and cleanup state. Output: a small record/template contract with stable evidence references, example receipt/handoff, applicability/uncertainty labels and private-versus-exportable fields. Raw outputs can remain separate local files; a reference is not proof those bytes remain available or authentic.

**Acceptance evidence.** A second reader identifies the unresolved question and exact next action. A successful command and a failed assertion remain distinct. Missing output, a moved/deleted reference, a human-supplied conclusion and a partial cleanup are represented without fabricated success. A sanitized export retains caveats while excluding a planted secret. A before/after example shows why this improves continuity over the existing artifact/file workflow.

**Dependencies and ownership.** H01 owns the shared evidence envelope if one is selected; H06 can reference it, H07 can use it, and teerex can attach Rex-specific references. They do not independently invent three competing evidence stores.

**Non-goals and gates.** No automatic summarizer, continuous recording, new storage service, trusted audit log, deployment certification or whole-machine resume. Before implementation, select the existing destination/storage and one real workflow; approve capture/export/retention separately.

## H02 — Opt-in friction instrumentation

**Origins:** Phase 1 #2, A03–A05, P1:pp2–3.

- **Who:** a future developer-workflow owner; Joshua selects the recurring annoyance and any collection permission.
- **What:** determine whether one manually confirmed repeated command sequence justifies a wrapper or automation proposal.
- **Why:** avoid building an invasive activity collector that produces speculative tools instead of saving work.
- **Where:** an existing workflow repository if selected, not teerex's observer or a new global telemetry service. Rex events are an optional separately reviewed adapter, not an assumed complete command-history feed.
- **When:** defer collection until a recurring problem and data source are named. Discovery can use a manually supplied synthetic sequence now.
- **How:** compare a hand-annotated sequence with the smallest per-command opt-in wrapper and specify exactly which fields it would retain.

**Inputs and outputs.** Inputs: one repeated repair/diagnostic workflow, its context variations, manually supplied examples and unacceptable data. Output: a bounded collection proposal or no-build recommendation, consent/disable/delete behavior, retention/export rules and one proposed automation with explicit applicability and refusal cases.

**Acceptance evidence.** Distinguish a meaningful repeat from two superficially similar commands in different directories/environments. Show a case that must not produce an automation suggestion. Demonstrate how secrets/argv/history are excluded rather than relying on retrospective redaction. State what time or errors the proposed tool could plausibly save; do not assert measured benefit from occurrence counts alone.

**Dependencies and ownership.** H01 may hold evidence; it is not a prerequisite service. A selected wrapper owns only its selected input. No changes to filed teerex issues or shell-wide hooks.

**Non-goals and gates.** No silent shell history, keystroke logging, weekly schedule, universal miner or auto-executed generated script. A real project, collection scope and opt-in permission are missing decisions; without them the output ends at the specification.

## H03 — PTY capture, replay and live-TUI compatibility

**Origins:** Phase 1 #3/#4, A06–A08, P1:pp3–4; generic parts of Phase 3 #6, C18–C20, P2:pp5–6.

- **Who:** a future terminal-test owner; an eventual teerex adapter owner remains responsible for Rex integration.
- **What:** scope a bounded capture/observer-replay fixture and, separately, a disposable live action test for one chosen TUI.
- **Why:** replay can test an observer while a live test checks actual input effects; conflating them would falsely validate a maneuver.
- **Where:** destination and TUI undecided. Reuse an existing PTY/test tool before extracting a library. Do not edit teerex's gesture layer or redistribute Rex.
- **When:** scope feasibility after a real support or maneuver-testing use case is selected. Live consequential automation remains behind teerex's host-input gates.
- **How:** investigate documented capture, libghostty embedding/version/license constraints and deterministic resize handling. Specify observer replay and live action as different test modes.

**Inputs and outputs.** Inputs: selected application/version, supported byte source, terminal dimensions/resize sequence, encoding and explicit capture consent. Output: a provenance-preserving fixture format or existing-format recommendation, feasibility/licensing findings, byte/time bounds and one observer/live acceptance design. No claim that a screenshot or replay reconstructs a machine.

**Acceptance evidence.** Cases include a split UTF-8 sequence, resize during a prompt, multiline error, progress change and destructive confirmation. Observer replay must preserve the selected display facts; a changed application response must fail a live action test even when an old recording still replays successfully. Missing bytes, unsupported embedding and nondeterminism have explicit outcomes.

**Dependencies and ownership.** H04 can define a required isolation boundary. Rex-specific guarded dispatch and takeover stay C05/C07/C16/C17; generic fixtures do not manufacture those guarantees. Reuse teerex's existing tests where sufficient rather than recasting shipped tests as missing infrastructure.

**Non-goals and gates.** No universal terminal emulator, whole-machine recorder, blind macro replay or learned maneuver engine. Before implementation: choose the application, capture rights, embedding/distribution terms, execution boundary and fixture publication policy.

## H04 — Authority, isolation and privacy boundaries

**Origins:** generic portions of A10/A11 (P1:p4), B01/B03/B04 (P1:pp6–7), C15 (P2:p4) and C28 (P2:p7).

- **Who:** a future security/platform owner; Joshua approves the threat model and authority granted.
- **What:** specify the smallest enforceable boundary for one selected workflow, preferring an existing sandbox/credential mechanism over a new broker.
- **Why:** a local allowlist, cooperative lease or visible pane cannot enforce all privileged paths.
- **Where:** existing platform/consumer repository if chosen. teerex retains its own safety obligations and existing scoped-channel/fence integration. This brief does not take over the externally owned fenced/remote-channel issues.
- **When:** before enabling a selected workflow that requires isolation or stronger authority, not as a prerequisite platform for every read-only utility.
- **How:** enumerate the protected resource, principals, allowed operations, bypass routes and revocation limits. Inspect existing enforcement first.

**Inputs and outputs.** Inputs: one concrete execution topology, credentials/files/network to protect, child/descendant requirements, existing sandbox configuration and separately approved sanitized material. Output: a threat/authority matrix, integration boundary, denied/bypass/revocation tests and a reuse/build/defer decision. Review the [current agent source contract](https://github.com/jcbbge/teerex/blob/f31de8c27e37c8e2934418739c4603f2c57e8c9f/items/agents/README.md): local scoped delivery and real bubblewrap acceptance exist; remote compute plus that channel still refuses. Do not duplicate those mechanisms or generalize their evidence beyond their tested scope.

**Acceptance evidence.** Include direct socket/store bypass, wrong recipient/token, expired capability, descendant escape and lost acknowledgement appropriate to the selected boundary. Explain what remains possible for same-UID/root processes. Distinguish reporting consent from enforcing it and a local lock from a Rex input lease. Missing enforcement is a failing requirement or explicit exclusion, not a new metadata field.

**Dependencies and ownership.** H05 consumes only the selected execution boundary. Rex-wide conditional input and immediate human revocation require supported host/application cooperation; no generic broker spec closes C07/C17.

**Non-goals and gates.** No universal “safe assistant,” second sandbox platform, production credential access, global userns/host-policy changes or silent redaction guarantee. The actual threat model, protected resources and permissible enforcement mechanism are missing selection gates.

## H05 — Task contracts, experiments and interruption semantics

**Origins:** Phase 2 #1/#2/#4, B01–B04/B08/B09, P1:pp6–9; B18 is the pp11–12 recap, not another runtime to build.

- **Who:** a future agent-workflow/runtime owner; Joshua selects the actual agent environment. No new owner is assigned to existing teerex migration work.
- **What:** specify one continuity slice: task outcome/boundaries, one isolated experiment, a changed assumption, pause/continue and a reviewable handoff.
- **Why:** make interruption invalidate the right work without losing evidence or pretending every child has stopped.
- **Where:** reuse the chosen agent environment or agent-core facilities if appropriate. Generic task reasoning belongs outside teerex; Rex surfaces/boards/ACK/jobs and paired replacement adapters remain teerex product work.
- **When:** after inspecting existing task/workspace facilities and identifying a concrete gap. Do not commission a new orchestrator merely to implement the original recap.
- **How:** define observable state transitions for one experiment and trace resources and pending work across an operator change.

**Inputs and outputs.** Inputs: selected task contract, permissions/budget, one invalidating change, existing cancellation/workspace APIs and evidence references. Output: a small state/permission contract, resource-ownership table, interruption/dependency-invalidating scenarios and recommendation for documentation, an adapter or a narrowly scoped implementation.

**Acceptance evidence.** Pause stops scheduling new work without claiming arbitrary descendant death; explain leaves execution unchanged; wrong-direction abandons the old approach while retaining evidence; continue does not revive invalid assumptions; takeover reports exactly which resource control was relinquished. A noncooperating child and an already-issued external effect remain visible limitations. Promotion produces a reviewable diff plus actual verification evidence.

**Dependencies and ownership.** H01 owns generic experiment evidence, H04 any required enforcement. Existing teerex agents/channel/migration and externally owned issue work are dependencies to consume, not a runtime to rebuild here.

**Non-goals and gates.** No general multi-agent controller, new cloud workspace service, automatic pause of arbitrary agents, private harness edits or personal launcher changes. Select the actual environment, one gap and budgets before implementation; real paid-agent evaluation needs separate approval.

## H06 — Causal decisions, knowledge view and counterfactual ledger

**Origins:** Phase 2 #3/#5 and ledger, B06/B07/B10/B11/B17, P1:pp8–9,11.

- **Who:** a future knowledge/workflow owner, with Joshua choosing one consequential decision workflow.
- **What:** specify manual claims/decisions linked to evidence, applicability, invalidators, rejected alternatives and revisit conditions.
- **Why:** prevent a dated observation or plausible summary from becoming permanent truth.
- **Where:** an existing document/artifact repository if selected. Rex is an optional evidence source, not a truth authority; do not add a knowledge service to teerex.
- **When:** after trying a few manual records using current storage. A dashboard or graph is not the first deliverable.
- **How:** work through one decision, a changed environment and contradictory evidence, keeping observed/inferred/chosen states separate.

**Inputs and outputs.** Inputs: H01-style evidence links or existing equivalents, decision scope, important rejected alternative and one invalidator. Output: minimal record/view rules, example conflict/revalidation sequence, migration path from existing notes and a no-build option. If a record envelope is shared, H01 owns it; H06 owns interpretation/applicability rules rather than a second evidence store.

**Acceptance evidence.** A changed version invalidates only dependent claims. Contradictory evidence stays navigable instead of being overwritten. An unresolved claim remains provisional. A rejected option is revisited only when its recorded condition changes. Deleted/unavailable evidence is explicit; no universal TTL silently certifies truth.

**Dependencies and ownership.** Existing records suffice; no retrieval service, embedding provider or teerex change is required for specification.

**Non-goals and gates.** No automatic truth maintenance, universal memory, internal-monologue feed, model training or autonomous consequential decisions. Choose storage, users, retrieval need and data permissions before selecting software or any paid-model experiment.

## H07 — Prepared questions and attention policy

**Origins:** Phase 2 #6/#7, B12–B14, P1:pp9–10.

- **Who:** a future agent-workflow documentation owner; Joshua sets escalation preferences.
- **What:** prepare a concise checkpoint/question practice with options, tradeoffs, recommendation, blocked dependency, safe default and work that can continue.
- **Why:** reduce avoidable interruptions without hiding irreversible/security decisions.
- **Where:** an existing prompt/skill/workflow document chosen by its owner, not automatically a new teerex cartridge, server or plugin.
- **When:** a low-cost early scoping candidate alongside H01; deployment into an agent's instructions is a separate reviewed change.
- **How:** compare existing guidance with representative situations and retain only a missing behavior. Prefer a small amendment over another overlapping policy layer.

**Inputs and outputs.** Inputs: current approved agent guidance, Joshua's escalation preferences and sanitized example situations. Output: a proposed minimal template/rule change, scenario-based acceptance rubric and unresolved policy decisions. Do not invent “one interruption per hour” or any other numerical attention budget.

**Acceptance evidence.** An ordinary reversible choice proceeds without a question; an irreversible action with no permission still requires approval; a blocked task asks a prepared question while independent authorized work continues; contradictory permission remains unresolved rather than silently broadened. A private capture never becomes an example without consent.

**Dependencies and ownership.** H01/H05 may supply task/evidence references, but no platform dependency is required. teerex's typed decision cards are a transport/presentation interface, not a reason to reimplement attention policy there.

**Non-goals and gates.** No attention surveillance, notification daemon, new agent, prompt deployment or claimed model-behavior improvement. Before a real model evaluation, separately approve the cases, model, cost and fresh-run count; a rubric or dry review is not empirical behavior validation.

## H08 — Observation, streaming and measurement support

**Origins:** generic portions of C03/C04/C10/C21–C24/C32, P2:pp2,4,6–8.

- **Who:** a future observation/evaluation owner only if a second real consumer appears. teerex owns its own evidence contract and measurements now.
- **What:** specify reusable data/measurement semantics where reuse is demonstrated; do not extract shipped support code solely because it could be a library.
- **Why:** avoid competing definitions of equal/quiet/unknown/completed and misleading productivity benchmarks.
- **Where:** prefer support code in the existing consumer. Destination and independent consumer are undecided; teerex's bounded chunks/comparison/cache remain there unless a separate extraction is justified.
- **When:** after the teerex C31/C32 safe-subset baseline or another consumer supplies a concrete need. No external engine blocks that baseline.
- **How:** use asymmetric fixtures and independently defined expected facts to distinguish exact equality, bounded incompleteness, cosmetic presentation and actual process exit.

**Inputs and outputs.** Inputs: documented observation schema, synthetic partial/unknown samples, one consumer use case and workload/metric definitions. Output: shared terminology, bounded fixture cases, metric collection contract and an extraction/no-extraction recommendation. Semantic classification, stream handling and benchmark infrastructure are separate choices, not a compulsory bundle.

**Acceptance evidence.** Equal visible prefixes with different hidden tails remain incomplete; a spinner change can be cosmetic only in an explicitly chosen view; an error/prompt cannot disappear silently; a retained done report is not direct-child exit. Resource/call/byte/latency measures name the processes and sampling domain. Claims about model turns, interruptions or user errors require actual corresponding observation, not proxy byte counts.

**Dependencies and ownership.** H03 can supply generic observer fixtures; H01 can reference evidence. Rex acquisition, source/target identity, status provenance and concrete teerex performance acceptance stay in teerex. Coordinate any eventual extraction; no parallel rewrites of C10/comparison/filter code.

**Non-goals and gates.** No universal idle/completion classifier, authority lease service, automatic screen normalization, general benchmark platform or unsupported improvement percentage. Choose a second consumer or specific missing semantic/measurement need before implementation.

## Paired agent-core migration is an existing product dependency

This is a **reference scope for the existing migration owner**, not a new H project or an assignment to work filed issue #11. The later operating-layer brief superseded the historical statement that all agent-core adoption lay outside teerex. The [current source boundary](../alpha5.md#migration-without-losing-working-behavior) and [public alpha.5 delivery guide](../releases/v0.1.0-alpha.5.md) govern; future delegates must inspect latest public source rather than assume that release includes later changes.

- **Who:** the existing externally owned migration/integration work, Joshua as consumer/approver; no duplicate owner created.
- **What:** pair each selected teerex replacement with the consumer invocation, parity evidence and a separately authorized removal/cutover plan.
- **Why:** a matching command name must not remove behavior carried by working wrappers, guards, relay or restart accounting.
- **Where:** teerex owns the supported replacement command/contract; `jcbbge/agent-core-public` owns caller adapters and retained stopgaps. Its historical inspected base is `c26bcfc`, not a verified current checkout. Actual private configuration belongs to Joshua and is not presumed supplied or shared.
- **When:** consume the issue owner's accepted implementation; finish parity before cutover; request host-specific rollout separately.
- **How:** compare each current caller with its replacement on the same disposable workload, publish the paired diff and retain fallback until the agreed acceptance and authorization are present.

**Inputs and outputs.** Required inputs include the exact current agent-core checkout, selected real harness/config/custom guards, approved private restart/tab-accounting source and exact topology. Outputs are a capability-to-caller matrix, no-loss paired patch, denial/uncertainty/exit/notification evidence, retained-boundary list and rollback/cutover plan. Existing migration guides under `items/{run,boards,surfaces}/MIGRATION.md` are inputs, not proof cutover occurred.

**Acceptance evidence.** Check literal argv/protocol, token-and-address ACK before one brief, actual versus reported termination, starter/report-to and seat/inbox semantics, visible/focusable/closable resources, fences, unknown outcomes, and recovery omissions. Use the managed path, not a direct-payload bypass. Real harness hooks/resume/custom guards and restart accounting require their actual approved inputs; synthetic hooks do not certify them. Remote compute plus local scoped delivery remains refused, not silently routed through a relay bypass.

**Non-goals and approval gates.** Do not duplicate filed-issue implementation, delete relay/wrappers/guards, edit personal settings, replace global launchers, install on M5/hive/M1/VPS, close panes or restart Rex based on this plan. Missing private inputs block their parity claim, not all other teerex work. Joshua separately authorizes the concrete deletion/cutover and each personal-host action after review.

## Recommended delegation preparation order

1. **H01 and H07:** smallest record/practice specs, using existing documents. They can be prepared independently and then reviewed together for duplicated fields/instructions.
2. **H03 and H04:** targeted feasibility/threat specifications only when a concrete TUI support case or protected workflow is selected. Neither blocks manual Rex continuity or read-only acceptance.
3. **H05 and H06:** gap analysis against the chosen runtime/current notes before any platform proposal. Prefer the smallest missing adapter/record.
4. **H02 and H08:** defer collection/extraction until an actual repeated problem or second consumer supplies the missing evidence.

All eight briefs are ready to hand to a scoping delegate with this shared contract. None starts a worker, chooses a new repository, selects an unapproved product or authorizes outside implementation.
